Services throughout a voyage

These run alongside implementation and review. They preserve decisions, execution evidence, and results without replacing the publication gates.

Agent Questions

  1. The agent saves a run-bound question and deadline.
  2. The operator replies on Agent Questions; the agent reads the answer and continues.
  3. Missing, expired, or cancelled required answers block completion and publication. Waiting retains capacity.

Contacts are optional suggested respondents. They do not send notifications.

Evidence and recovery

  1. The host validates reports, then records immutable artifacts and content hashes.
  2. After restart, reattach the durable process or container identity.
  3. For checkpoint continuation, verify the frozen snapshot, saved artifacts, branch, base, and head before reusing work.

A fresh retry preserves the original task/provider and Docker image pin. Prompt or skill drift blocks preflight.

Current setup and limits: Docker needs a built image, host provider keys, and pre-provisioned dependencies; agent stages have no unrestricted internet access. Docker branch-update reruns currently fail preflight; select trusted local execution for that mode. Webhook secrets, mappings, and public ingress require configuration. Offline Docker and mocked gateway flows were tested; real provider-backed Docker validation still requires host API keys. No path automatically merges a PR.

Review selection and concurrency

The writer CLI must be available in the selected execution environment. If the alternate CLI is unavailable, one reviewer is allowed even when two are configured. Lead sessions run sequentially; prompts request concurrent focused sub-agents, but runtime does not verify delegation.

Round and session limits

Configuration allows 1–2 reviewers, 1–5 rounds, and 5–180 minutes per session. Summary correction gets one separate session per report and does not use another review round. The 2,000-character limit uses JavaScript string length, including whitespace and bylines.

Resume preserved work

A valid checkpoint verifies saved artifact hashes and its frozen snapshot, skips implementation, and reuses the original reports for its saved review round. The current branch, base, head, and complete reviewer set must match. Legacy checkpoints without manifests use an explicit compatibility path. Oversized saved summaries can use the same correction step.

Publication and follow-up boundaries

Pre-PR voyages have one outer attempt. Failures preserve work; a push may already have happened if a later publication check fails. Jira transitions apply to eligible Jira tasks, not todos or freeform tasks. The separate Helmsman review waits for availability and may reuse an existing review of the current head.
